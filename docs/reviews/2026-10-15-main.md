## Summary

The parent authentication and household setup implementation establishes a clean boundary protecting child privacy. Registration, password authentication, magic links, and session cookies via Supabase Auth function smoothly with complete test coverage. Before merging, three major issues should be addressed: an open redirect risk in post authentication navigation, an unvalidated origin parameter in magic link emails, and database migrations missing Row Level Security policies for profiles.

## Major

### 🟠 Open redirect in post authentication navigation, `apps/web/src/app/(auth)/actions.ts:108` and `apps/web/src/app/auth/callback/route.ts:13`

**Problem**: The `nextUrl` parameter in `signInParentAction` and the `next` search parameter in `route.ts` accept arbitrary target paths without validation. If an attacker passes an external address such as `https://evil.com` or `//evil.com`, Next.js `redirect()` and `NextResponse.redirect()` will route the user to that external location.
**Why it matters**: Phishing campaigns can use legitimate Kid Zone login links to redirect parents to malicious sites immediately after entering credentials.
**Suggested fix**: Validate that the redirect target is a safe local relative path (for example, verifying it starts with a single `/` and does not start with `//` or `/\`).

### 🟠 Unvalidated origin parameter in magic link request, `apps/web/src/app/(auth)/actions.ts:134`

**Problem**: `signInMagicLinkAction` accepts an `origin` string argument passed directly from the browser client, constructing `redirectTo` without server verification.
**Why it matters**: A malicious client could supply an external domain, which may lead to token delivery to unintended locations if redirect URL patterns in Supabase are broad.
**Suggested fix**: Derive the application URL on the server using Next.js request headers or the configured `NEXT_PUBLIC_SITE_URL` environment variable rather than accepting a client supplied origin string.

### 🟠 Profile table Row Level Security policies missing from versioned migrations, `packages/db/drizzle/0002_rls_policies.sql:1`

**Problem**: Row Level Security is enabled on the `profiles` table in `0001_tough_lilandra.sql`, but the policies granting owner read and write access exist only in `supabase/sql/auth.sql` and are omitted from `0002_rls_policies.sql`.
**Why it matters**: Running `pnpm db:migrate` in a clean environment creates the table with security enabled but zero policies, causing queries against `profiles` to return empty sets or fail.
**Suggested fix**: Move the `profiles` Row Level Security policies into a versioned migration file inside `packages/db/drizzle/` so standard database migrations apply them automatically.

## Minor

### 🟡 Database write inside Server Component render, `apps/web/src/app/parent/page.tsx:24`

**Problem**: `ParentDashboardPage` executes upsert mutations against `profiles` and `households` during server component rendering if records are not found.
**Why it matters**: Next.js Server Components should remain pure read operations. Running mutations during rendering can trigger unintended writes during streaming, revalidation, or page prefetching.
**Suggested fix**: Rely on the database user creation trigger for provisioning, or handle missing records with an explicit action rather than writing inside the render pass.

### 🟡 Confusing message when email confirmation is required, `apps/web/src/app/(auth)/actions.ts:66`

**Problem**: When Supabase requires email confirmation and returns no initial session, `signUpParentAction` returns a message saying the parent may explore their dashboard now.
**Why it matters**: Unconfirmed users without an active session cannot view the protected dashboard and are immediately redirected to the login screen.
**Suggested fix**: Adjust the return message to ask the parent to verify their email before attempting to open the dashboard.
